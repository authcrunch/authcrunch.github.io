# Documentation

## Ownership and inputs

Own public content in [docs](../../../docs/), [blog](../../../blog/), and simple
Markdown pages under [src/pages](../../../src/pages/). Start with the reader's
task, affected topic, supported product version, and existing adjacent pages.
The output should explain the supported behavior and keep navigation, examples,
and linked assets consistent. Site components and build tooling have separate
owners in the root routes.

| Topic | Existing home |
| --- | --- |
| Installation and first steps | `docs/intro.md`, `docs/start/`; existing authenticate/authorize getting-started pages link into this sequence |
| Topic discovery, reference, and diagnostics entrances | `docs/guides.md`, `docs/reference.md`, `docs/troubleshoot.md` |
| Portal, cookies, challenges, transforms, and UI customization | `docs/authenticate/` |
| Local, LDAP, OAuth/OIDC, SAML, X.509, and web app integration | Corresponding subdirectories of `docs/authenticate/` |
| Portal, profile, server, and system APIs | `docs/authenticate/api/` |
| Policies, tokens, ACLs, headers, and authorization methods | `docs/authorize/` |
| Credentials, messaging, SSO apps, and community examples | `docs/credentials/`, `docs/messaging/`, `docs/apps/`, `docs/examples/` |
| Dated articles and walkthroughs | `blog/YYYY-MM-DD-topic.md` |

Use [configuration-examples](../configuration-examples/SKILL.md) to author, correct, or validate Caddyfile snippets, runnable examples, and their environment or solution assets.

## Routes, structure, and assets

The [sidebar](../../../sidebars.ts) gives `intro` and `start/` their own learning
sequence. A second sidebar includes the three subject entrances and explicitly
named categories with autogenerated contents. Within those categories,
`_category_.json` supplies nested directory labels and positions; frontmatter can
supply `title`, `sidebar_position`, `id`, or `slug`. Existing content mixes
frontmatter positions with numeric filename prefixes. Preserve published IDs,
URLs, and heading anchors when possible. Before a rename, search inbound Markdown
links and [navbar/footer configuration](../../../docusaurus.config.ts), then
verify the resulting routes; do not infer a URL solely from a numbered filename.

Use relative `.md` links to neighboring documents where practical. Resolve
screenshots relative to the page: some live in the parent's `images/`, others
under provider-specific `images/` directories. Keep descriptive alt text and
check every changed path. Files under `static/` have public paths without the
`static` prefix; `assets/conf/` and `assets/solutions/` are repository examples,
not automatically copied site downloads.

The beginner and GitHub Caddyfiles are imported from
[assets/conf/getting-started/Caddyfile](../../../assets/conf/getting-started/Caddyfile)
and [assets/conf/oauth/github/Caddyfile](../../../assets/conf/oauth/github/Caddyfile)
using `?raw` and rendered by `CodeBlock` in their walkthroughs. Edit those
canonical files instead of adding duplicate complete fenced configurations. The
site plugin resolves them at build time; imports do not create download URLs.

Some pages still link to `greenpau/caddy-auth-docs`. When updating one, verify
the corresponding file here and use the current
`authcrunch/authcrunch.github.io` repository URL. Avoid unrelated link rewrites.

## MDX and factual guidance

Every current document needs explicit discovery metadata. A listed document has
an accurate `description` and a `discovery` object with `topic` and `kind` from
[the shared vocabulary](../../../src/discovery/catalog.ts). Optional `aliases`
hold familiar names for content actually covered, such as Azure AD for Microsoft
Entra ID. Do not add aliases for missing features merely to satisfy a query.
The build validates this metadata and derives the directory from resolved URLs.

Set `listed: false` within `discovery` for a useful search destination that
should not duplicate an entry in the directory. Set `discovery: {exclude: true}`
for placeholders, obsolete screenshot galleries, or duplicate directories;
do not advertise them as completed guides. Exclusions preserve published routes.
Draft and unlisted pages are also omitted. Completing an excluded page requires
adding its description and classification to make it discoverable again.
Classification alone does not establish that its configuration is up to date.
The [search maintenance guide](../../../assets/search/README.md) describes how
this metadata reaches hosted search after deployment and crawling.

The [site config](../../../docusaurus.config.ts) compiles Markdown as MDX. Put
Caddy placeholders, JSON braces, template syntax, and angle-bracket placeholders
in inline code or fenced blocks. Use `[text](url)` for links instead of `<url>`
autolinks, which MDX parses as JSX. Use `{/* comment */}` for comments instead
of HTML comments; `future.v4` disables the MDX 1 compatibility transforms.
Raw JSX/HTML must be valid MDX. Preserve
admonitions, tables, and code-fence boundaries when editing examples.
Use the current titled-admonition syntax, such as `:::warning[Local example]`,
with blank lines around its contents. Under `future.v4`, legacy titles separated
by a space can render as literal text without failing the build. Inspect the
rendered callout, not just the build exit status.

Verify syntax and behavior at the relevant implementation boundary rather than
treating an existing page as conclusive evidence. For API work, check method,
route prefix, authentication/role requirements, request and response shape, and
failure behavior in the selected upstream source. A handler's existence does
not establish that a public Caddy directive enables it. Mark incomplete or
version-limited behavior explicitly instead of filling gaps with assumptions.
For changing provider-console steps, consult current official provider material;
existing screenshots can be historical.

New walkthroughs should identify prerequisites, exact configuration placement,
expected outcomes, and material failure cases. Use synthetic credentials and
explain demo-only settings. A documentation build proves rendering and link
checks, not successful authentication or an external provider integration.
Pin the executable bundle and its library version separately. A newer sibling
checkout or local tag is not proof that behavior is included in a published
bundle. Distinguish portal token policies, direct OAuth sessions, and AuthCrunch
acting as an OIDC provider when describing login or token lifecycle settings.

## Blog workflow

Follow the existing dated filename pattern. Set a stable `slug`, meaningful
`title`, and author key from [authors.yml](../../../blog/authors.yml); add an
author record only when needed. Include `{/* truncate */}` after the introduction
for the list/feed excerpt. Existing posts use inline tags and the site warns
about inline tags, inline authors, and untruncated posts. Review warnings in
context instead of disabling them globally for a single article.

## Verification and acceptance

Run `npm run build` for public content changes and inspect new warnings as well
as failures. Broken site links throw; broken Markdown links are configured to
warn. A zero exit status does not replace review of warnings or external links.
The operational command details are in
[site-operations](../site-operations/SKILL.md).

- A new provider page appears in the intended category and its images, example
  link, and callback URI agree with the described portal mount path.
- A renamed page preserves its URL or has an explicitly implemented migration;
  inbound links, navbar IDs, and changed anchors resolve after the build.
- A new API example states the applicable role and response behavior with source
  evidence; unavailable runtime checks remain identified as unverified.
- A blog post has a working author, stable route, and useful excerpt, with no
  new unexplained MDX or link diagnostics.
- The beginner sequence has usable previous/next navigation, a complete example,
  an observed login and allow/deny boundary, and a logout check. Topic entrance
  links preserve the destination pages' current published routes.
