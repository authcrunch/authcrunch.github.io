# X.509 Configuration

The released Caddy Security v1.3.0 / go-authcrunch v1.3.8 adapter does **not** expose an X.509 identity provider that turns a client certificate into a portal user or JWT. Its login integrations are local, LDAP, OAuth/OIDC and SAML. An old placeholder page is not evidence of certificate-login support.

## Choose the certificate's purpose

| Certificate/key use | Owning layer | What it proves |
| --- | --- | --- |
| Server HTTPS certificate | Caddy TLS | The browser/server TLS identity |
| Required, verified client certificate | Caddy TLS client authentication | A client holds a key trusted by the configured TLS policy |
| SAML IdP signing certificate | [SAML provider](../saml/10-saml.md) | An assertion is signed by the separately pinned IdP key |
| Portal JWT signing key/public JWKS | [Token verification](../../authorize/token-verification.md) | A token's issuer/key signature, subject to policy validation |

Caddy's [TLS client-authentication controls](https://caddyserver.com/docs/caddyfile/directives/tls#client_auth) support requiring and verifying client certificates against a configured trust pool. Requiring a certificate without verification is a different mode; choose and test the intended trust boundary using the exact Caddy version you run.

## Combine transport and application access

A verified client certificate can gate the TLS connection, while AuthCrunch separately authorizes application access from a supported identity source. Passing the TLS check does not automatically create `sub`, `email` or application roles, enroll a local account, or bypass JWT/ACL validation.

If TLS terminates at another proxy, this Caddy instance does not receive the original client's TLS handshake. A forwarded certificate header needs a separately designed trusted-proxy and identity-mapping boundary; accepting a browser-supplied header is not certificate verification. Keep backend reachability and header normalization explicit.

For a working learning path, begin with [your first protected app](../../start/first-app.md), then select a documented identity provider. For certificate-gated deployments, verify rejection with no certificate, an untrusted certificate and an otherwise authenticated user without the required app role. This page does not provide an unsupported `x509 identity provider` directive.
